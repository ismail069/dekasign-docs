## Per-document flow
<Note>
The classification, saved preparation templates, and Process policy below were tested locally in the 20 October 2026 update. Migration and deployment remain separate. Confirm that your workspace uses the corresponding release before following this flow.
</Note>

The workflow must enable request-document signing. After upload, choose each document's purpose:

| Choice | Use |
| --- | --- |
| **Attachment** | An ordinary attachment to review. |
| **Supporting document** | Supporting evidence to review. |
| **Document to sign** | A document requiring digital or visual signing. |

For **Document to sign**, open the editor, select Actors/signers and **Digital Only** or **Visible Signature**, and configure the required fields. Click **Save & attach to form** to save a private template and attach it automatically. It is bound to that file, release, and layout; you do not need to create a standalone template first.

Signing documents allow up to 15 MB/file. You can save a draft before preparation is complete, but **Submit** is refused until every signing document has valid saved preparation.

Open the selected document's editor and assign Actors/signers and fields/areas according to supported policy. Request documents follow the design and approvers actually visited; unexecuted branches do not automatically become signers.

## Assign every field
The form/workflow Document Sign Editor uses workflow Actor slots. For **every** text, multiline, number, date/place, checkbox and signature field, select its responsible Actor in **Filled by** or **Signature supplied by**. Optional values still need an assigned Actor. Unmapped or invalid ownership blocks saving and server submission.

Digital-only Actors can fill non-signature fields without a signature rectangle. Visible signature fields belong only to visual-signature slots. This editor ends with **Save & attach to form**. Standalone Document Sign has a separate recipient editor and prepare/send flow.

In Canvas, select an Actor and choose **New document signing default**: **Digital Only** or **Visual Signature**. New documents take defaults from the workflow release pinned to the upload, not the latest draft. Visual mode still requires placing a signature rectangle. Saved documents retain their own modes and assignments.

Each document supports up to 20 signing Actors. For a larger workflow, remove an unneeded slot and choose another Actor from the workflow catalog.

The two editor entries, mandatory field mapping and mode defaults passed local checks in the 21 October update. Desktop checks cover upload, Save & attach, reopening a template and standalone Ready. Complete requester-supplied external identity/audience handling, mobile acceptance and deployment remain separate; they are not activated by this guide.

## Review
Approvers review form data, files, notes, and annotations before deciding. A note is not signing consent. Document approval and workflow approval must follow the configured permissions and modes.

In the document reviewer, open **Preview & download audit** to see who received a preview/download, when, and for which revision. This activity is separate from confirmation and decisions. Serving a file does not prove that its contents were read or approved.

In the local21 October update, private-document restrictions apply to **Attachment**, **Supporting document**, and **Document to sign**, including when the assigned approver is an Owner. An Owner who is not a participant gains no automatic file access; only the requester can change request attachment permissions. Participant downloads require explicit permission. When upload-wide and attachment-specific policies differ, the stricter restriction applies.

## Process usage
For new requests under this policy, one workflow uses **1 Process**, plus **1 Process for each distinct signing document**. Two signing documents and several ordinary attachments use **3 Processes**. Attachment and Supporting document do not add signing Processes.

The same original content is counted once in that request cycle, including additional approvers, retries, layout revisions, and reuploads. Different original content adds one Process when submitted in a later revision. Insufficient credit rolls back the complete submission transaction. Historical requests retain their previous policy; sandbox does not debit production credit.

## Document revisions
The requester reads revision instructions/annotations, replaces files or data as needed, and reviews signing plans before Resubmit. Evidence for an older version must not be presented as approval of a newer file.

## Results
Approved/signed documents retain action context and the evidence page provided by the system. Check the actor, time, and version/digest. Printing a final PDF to a new PDF does not preserve the same integrity evidence.

## API
Management API submissions support digital approval only for selected documents. API keys cannot create visual signatures or impersonate signers. API access remains sandbox-only; see the [request API](/en/api-reference/requests).

## Boundaries
Native signing uses internal DekaSign integrity, not a certified seal. External approval Actors and ALL/ANY activation are separate from external Document Sign recipients.
